# BANDO HUB: SQLite 관계형 업무 데이터 코어 (1단계)

## 목적과 적용 범위

현재 운영 단계는 Windows/Tauri 단일 PC 오프라인 앱이다. PostgreSQL, 공유 네트워크 파일 또는 유료 서버는 필요하지 않다. 비용과 리스크를 줄이기 위해 기존 React State/IPC 형식은 유지하되, **핵심 데이터의 실제 저장 위치**를 단일 `app_state` JSON에서 SQLite 테이블로 이동한다.

**이 브랜치에서 구현한 1단계 관계형 저장 원본**
- `core_products`: 상품 ID, 표시명, 모델코드, 원래 리스트 순서, 기타 상품 속성
- `core_variants`: 상품 ID를 참조하는 옵션, 색상, 도매/반도매/소매 가격, 옵션 ID
- `core_clients`: 거래처, 표시명, 등급, 주소와 기타 거래처 설정
- `core_orders`: 주문 ID, 거래처 참조용 값, 일시, 상태, 주문 기본 기록
- `core_recipients`: 주문 ID를 외래키로 참조하는 수취인
- `core_items`: 수취인 ID를 외래키로 참조하는 주문 품목, 등록 상품 및 판매 옵션 식별자

상품/주문/수취인의 중첩 JSON은 자식 배열을 떼어낸 **행별 속성 JSON**으로 보관하고, 해당 자식 목록은 별도의 테이블에서 복구한다. 주요 검색 필드는 개별 SQL 열과 인덱스를 사용하며, 고정 서식의 나머지 필드는 행별 JSON을 사용한다. 단일 전역 JSON을 무조건 무리하게 다수의 열로 펼치는 것보다 안전하고, 향후 필드 추가에도 견고한 절충안이다.

**아직 기존 `app_state`에 남겨두는 영역:** 송장/운임과 연결된 `workflow` 전반, 설정, 별칭, 카테고리, 배송 규칙, 공장 회신, 상품 매핑 및 기타 변경 추적 정보. 다음 차수에서 실제 업무 관계를 검증한 뒤 각각 분리한다. 관계형 코어를 도입했다고 *전체 업무 DB가 완전히 정규화된 것은 아니다.*

## 저장 일관성

- `core_schema`의 `business-core = 1`을 마이그레이션 완료 마커로 사용한다.
- 기존 앱 DB를 최초 열 때 `VACUUM INTO`로 원본 `pre-relational-*.sqlite` 백업을 **먼저 생성하고 검증한다**. 마이그레이션 실패 시 원본을 새 시드로 덮어쓰지 않는다.
- 기존 전체 JSON은 하나의 트랜잭션에서 관계형 행으로 전환하며, 이때 `app_state`에서 `products`, `clients`, `orders`를 제거한다. 따라서 이 셋은 더 이상 전역 JSON의 원본이 아니다.
- 기존 Tauri API `state_load`는 SQLite 행을 조립하여 이전 형식으로 응답한다. React 코드는 이식 없이 계속 동작한다.
- `write_snapshot`은 기존 리비전 충돌, 거래처 검증, 브랜드 검증, 접수/정정 감사 보호를 유지한다. 관계형 행 저장과 호환 메타 상태, 검색 인덱스, 접수 감사 기록을 **단일 트랜잭션**에서 처리한다.
- `PRAGMA foreign_keys=ON`을 연결 생성 시 활성화한다. 상품→옵션, 주문→수취인→주문 품목은 외래키로 강제한다.
- 삭제/보관된 거래처와 상품이 과거 확정 주문에 들어 있을 수 있으므로 과거 주문의 `client_id` 및 품목의 `product_id`에 강제 FK는 아직 걸지 않는다. 원본 ID는 유지하고 새 주문의 검증은 기존 Rust 접수 검증 계층에서 실행한다.
- 화면 설정만 변경한 경우 관계형 상품/주문 목록과 검색 인덱스를 일괄 다시 쓰지 않는다.
- SQLite FK 검사 및 스냅샷 구조 검증이 성공해야 정상 DB로 간주한다.

## 백업, 복구, 개발자 모드

- 기존 `backup_manager`는 SQLite 파일 전체를 검증하고 백업하며, 관계형 FK 검사까지 수행한다.
- 구형 전체 JSON 백업을 복원하면 관계형 코어로 다시 이전한 뒤 리비전을 높인다. 복원 직전의 안전 백업과 롤백 로직은 유지한다.
- 격리 TEST DB 초기화 때는 주문과 수취인/품목 관계형 행을 포함해 해당 테스트 활동만 지우고, 초기 상품/가격은 유지한다.
- 이 작업은 GitHub 개발 브랜치에만 적용한다. 이미 설치된 PC의 SQLite DB 파일은 이 변경만으로 즉시 수정되지 않는다. 신규 빌드를 실행할 때 기존 SQLite가 있으면 사전 백업 후 이전한다.

## 앞으로 별도 검토할 범위

1. `workflow` 내 출고, 송장, 입금, 주문 처리 이벤트, 운임, 결산의 SQL 모델. 감사 로그 원본과 동결 스냅샷 불변성 규칙을 먼저 확정한 다음 분리.
2. 장기 운영에서 더 이상 불필요한 `product_index`, `order_index` 호환 검색 캐시의 제거 또는 뷰 전환.
3. Windows 실제 기기에서 구 DB 열기, 앱 종료 후 재시작, 백업 복원, 개발자 TEST DB 초기화, 한국어 검색 및 공장 Excel 왕복 시험.
4. 이후 여러 PC를 연결해야 할 때 SQLite 파일을 네트워크 공유로 직접 열지 않고 중앙 API를 통해 접근하는 설계.

- `npm test` 및 TypeScript 타입 검사

- GitHub Actions `Verify Tauri migration (draft)`의 Windows SQLite, Rust, Tauri 실행 파일 빌드 작업
