# 반도허브 SQLite 관계형 저장 구조 v2: 독립 판매 상품 기준

## 확정 기준

- 반도허브는 오프라인 Windows Tauri 앱이며 SQLite를 그대로 사용한다.
- **한 판매 구성 = 한 독립 상품 ID**. 상품에 추가 옵션을 선택시키지 않는다.
- 판매 식별 문구는 상품명에 포함한다. 가방 포함과 미포함, 바퀴 포함과 미포함, 상판 형태, 색상, 길이, 규격, 구성품이 다르면 별개 상품이다.
- `상품설명`은 매장 직원에게만 보여주는 참고사항이다.
- 외부 홈페이지의 상품번호 및 옵션 코드는 **원본 데이터 연결용 기술 식별자**이며, 직원이 추가로 선택하는 옵션이 아니다.
- 동일 모델코드를 공유하는 개별 상품이 있을 수 있으므로 `code`만으로 합치거나 중복이라고 판단하지 않는다.

## 실제 SQLite 테이블

| 테이블 | 저장 내용 |
| --- | --- |
| `core_products` | 업무용 독립 상품 ID, 코드, 완전한 상품명, 행별 추가 속성 |
| `core_product_prices` | **상품 ID당 한 행**: 도매, 반도매, 소매, 색상 및 역사적 가격기록 ID, 공식 사이트 연결 정보 |
| `core_clients` | 거래처 정보 |
| `core_orders` | 주문, 거래처 참조, 확정 및 상태 정보 |
| `core_recipients` | 주문별 수취인 |
| `core_items` | 주문별 품목, 확정 당시 상품 식별 정보, 수취인 관계 |
| `receipt_archive` | 접수 원문 및 정정 감사 기록 |
| `app_state` | 아직 관계형 분리를 마치지 않은 설정, 별칭, 출고, 입금, 운임, 기타 워크플로 데이터 |
| `product_index`, `order_index` | 기존 검색 호환용 복제 인덱스. 관계형 정본이 아니므로 후속 제거 후보 |

`core_product_prices.product_id`는 기본키이자 `core_products.id`의 외래키이므로 하나의 상품에 가격 구성을 둘 이상 붙일 수 없다. 상품의 색상/원본 구성 정보는 현재 1개 호환 가격 기록 안에 남아 있으나, 앱 화면에는 옵션 선택으로 표시하지 않는다.

내부 Tauri/React API의 `variants[0]`, `variantId`, SQLite `core_items.variant_id`는 **과거 가격기록 ID 호환용**으로 당분간 남겨 두었다. 1개짜리 내부 호환 구조이지 직원에게 제공하는 판매 옵션 모델이 아니다. 전체 주문/가격/엑셀 코드의 호환 필드까지 한 번에 삭제하면 검증 범위가 불필요하게 커지므로, 기능 이식 안정화 후 별도 전환한다.

## 초기 데이터: 303개 사이트 목록과 360개 실제 상품

- 역사적 사이트 목록: `src-tauri/resources/legacy-state-seed-303.json`에 **303건**, 기존 가격 기록 **360건**을 변경 없이 보존.
- 현재 업무 상품 정본: `src-tauri/resources/state-seed.json`에 **360개 독립 상품**, 각각 **1개 가격 기록**.
- 모델과 구성에 따른 업무용 이름은 `docs/independent-products-360.md`에서 원본과 대조한다.
- 기존 도매/반도매/소매 가격, 사이트 상품번호, 사이트 옵션 코드 및 기존 가격기록 ID를 보존한다.
- 같은 이름으로 서로 다른 사이트 상품번호에 등록된 항목은 확인 근거 없이 합치지 않는다.

## 기존 개발 DB 이전

- 기존 SQLite 파일을 사용자가 이미 보유한다면 관계형 분리 전에 `pre-relational-*.sqlite` 원본 백업을 만든 다음, 체크된 트랜잭션에서 v2로 이전.
- 구형 저장 구조의 여러 가격기록을 독립 상품에 연결할 때는 원래 상품 ID와 **정확한 가격기록 ID**를 함께 사용한다. 매칭이 불명확한 자료가 있으면 이전을 중단하고 기존 DB 및 사전 백업을 보존한다.
- 확정된 과거 주문과 감사 스냅샷은 변경하지 않는다. 미확정 주문/별칭의 연결은 명확한 기록에만 재연결한다.
- `core_schema`의 `business-core=2`가 이전 완료 표식이며, 구형 물리적 `core_variants` 테이블은 이전 성공 시 트랜잭션 안에서 제거한다.
- 프런트에는 기존 `State` 형태로 재조립해 전달하지만, 실제 저장 정본은 개별 관계형 SQL 테이블이다.
- DB 리비전 비교, 감사 기록 불변성, 외래키 검사, 개발자 TEST 분리, SQLite 백업/복원을 유지한다.

## 아직 완료되지 않은 범위

1. 현장 Windows EXE 실행과 실제 주문, 출고, 공장 Excel, 정정 및 재실행 검증.
2. `workflow`의 배송, 입금, 운임, 정산 관계형 분리.
3. `variantId` 등 내부 가격기록 호환 필드의 이름과 프로토콜 정리.
4. 공식 홈페이지의 실제 최신 가격과 내부 수동 가격 동기화의 추가 대조.
5. 다중 PC 공동 DB 접근은 **지금 범위 아님**. 나중에 중앙 API로 설계하며 SQLite 파일 직접 공유는 피한다.

## 승인 및 배포 경계

이 변경은 개발 브랜치 / 기존 Draft PR에만 있으며 `main`에 병합하지 않았다. 앱 버전을 바꾸지 않았고 사용자가 보유한 SQLite 파일을 외부에서 삭제하거나 덮어쓰지 않았다. CI 시험 결과와 Windows 실사용 결과를 구별해 확인한다.
