- Rust 위치 검증: 위 전체 원문 근거의 `start/end`는 UTF-16 단위이고 원본 문자열과 일치

## 실제 수정한 Rust 오류

1. 반복 상품명 비교의 정규식 컴파일 캐시 적용. 원래 값과 매칭 우선순위는 변경하지 않음.
2. 수량과 수취인 이름이 같은 줄에 있는 발주서에서 상품 원문 범위를 수취인 앞에서 종료. 품목에 이름/전화번호가 섞이는 문제 해결.
3. 괄호형 우편번호는 배송주소 값과 근거 출처에서 분리하되 원문 UTF-16 위치 보존.
4. 모델명이 미확정된 상품의 표시명에서 말미의 수량 표현만 제외.
5. 품목 수량 미기재 시 원본 TS가 제거하는 중복 경고를 Rust에서도 제거. `quantityConfirmed=false`는 유지.
6. 주소 세부정보의 시/군/구, 읍/면/동/리 및 건물번호를 TS `addressParts` 순서/조건에 맞춰 정정. 비정상 광역시 문자열의 도 단위 오인 방지.
7. 화면 후보 근거를 실제 발주 원문 읽기 순서로 정렬하고, 상품 후보 표시 라벨과 상품 줄 기준 시작/끝 위치를 TS와 일치시킴.
8. 중복 연락처 증거가 추가 전화번호로 재배정될 때 출처 필드를 보정하고, 수취인 출처의 원문 순서를 보존.
9. 이름 뒤 직함 `목사` 등은 인식된 이름과 강조할 원문 구간을 구분.
10. `BD 709 (블랙)`처럼 모델과 괄호 색상이 구분된 경우 모델의 출처 범위를 별도로 정정.
11. `match.term`은 원본 TS와 같은 등록 별칭 → 세 자리 모델코드 → 전체 줄 순서로 선택.

기존 TypeScript, 업무 데이터, 사용자 UI 및 다른 세션의 전용 브랜치는 수정하지 않았다.

## 의도적으로 원본과 다른 3건

- **02:** 원본 TypeScript는 `김가상 예수아님`에서 직함/추가 문자열을 이름으로 함께 오인식하고 일부를 잘라냈다. Rust는 실 수취인 `김가상` 한 명으로 분리. 실제 비공개 원문 개인정보는 포함하지 않음.
- **19:** 원본 TypeScript는 주문 날짜를 허위 상품으로 인식하고 `연주용의자`를 사람 이름으로 취급하며 BB-3 수량을 잃음. Rust는 실제 수취인 `여가상`, 실 상품 BB-3 1개, 정상 배송지/연락처를 유지.
- **20:** 원본 TypeScript는 `발주일`을 별도 수취인으로 만들고 날짜를 상품으로 인식. Rust는 실제 수취인 `이가상`, Desk TS-2 1개, 정상 배송지/연락처를 유지.

3건 각각에 대해 허위 상품/수취인이 생성되지 않는지, 실제 상품 ID와 수량/확정/배송지/연락처를 확인하는 별도 단언을 유지한다. 이 예외를 일반 불일치로 감추거나 원본 오류를 Rust에 복제해서 통과시키지 않는다.

## 검증하지 않은 범위

1. 이 20건 및 `src-tauri/resources/state-seed.json` 이외의 발주서, 모든 360개 독립 상품 입력 조합, 비표준 외부 OCR 텍스트 조합까지 보장하지 않는다.
2. 원본/이전 주문의 직원 수동 확정값 병합, 실제 SQLite 영속/복원, Tauri IPC, React 표시, Windows GUI 및 PaddleOCR 경로에 대한 **엔드투엔드 동등성은 미검증**.
3. 자동 생성 식별자, 후보의 설명용 `reason`, 페이지별 부가 메타데이터, 미연결 증거 ID, 일부 진단용 부속 필드는 완전한 1:1 스냅샷 비교를 하지 않았다. 사용자 업무 판단을 바꾸는지 별도 전수 감사가 필요하다.
4. `migration/01-recognition` 전용 브랜치에 자동 병합하지 않았다. 해당 브랜치는 다른 세션 작업 중이었으므로 **충돌을 피하기 위해 별도 브랜치**에서 검증했다.
5. 이것만으로 제품/가격/운임/출고 전체 Rust 이전 성공, 프로덕션 번들의 기존 TypeScript 업무 로직 제거, 2026-11-14 시연 승인을 선언할 수 없다.
